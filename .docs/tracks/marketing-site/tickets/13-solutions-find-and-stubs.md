# 13: Solutions pages, the marketplace shell, and the stubs

**What to build:** The last of the routes, and the one place this track reaches forward: the
marketplace shell's parameter names are defined now so Sprint 011 inherits the
vocabulary instead of coining a second one. The stubs exist so that no
navigation item 404s — which is an acceptance criterion, not tidiness.

**Blocked by:** 03

**Status:** ready-for-agent

- [ ] Four solutions pages, one per audience the product actually serves — including land-selling companies, which are a first-class customer and not a footnote.
- [ ] A marketplace shell whose URL parameter names are **defined in the shared contracts package**, so Sprint 011's listing service inherits them. Filter shapes that are not yet settled are marked as assumptions with no default.
- [ ] The shell runs against demo data. No real listing data, and no listing service — it does not exist.
- [ ] No map library. A static map image only, because the library would consume the entire JavaScript budget for a decorative element.
- [ ] Four legal stubs with a **visible "in review" banner**, plus a resources stub and a status stub, so every navigation and footer target resolves (DEBT-09).
- [ ] **No invented legal text.** An unreviewed privacy policy that reads as reviewed is worse than an honest stub (Q6).
- [ ] No blog. The resources page is a stub, because an empty blog reads worse than no blog.
